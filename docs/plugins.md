# Plugins in Setup

Open **Setup → Instructions & skills → Plugins** to inspect complete agent packages. A plugin may include skills, tools, agents, rules and automatic commands. Importing its instruction folders through Skills does not install the complete plugin.

## Current support

The library reads personal plugin files without running them. It covers Codex and Claude caches, local Cursor/Grok/Antigravity plugin folders, and local OpenCode/Pi declarations. Coverage is explained under **Inventory coverage and agent support**. Project, managed and live session inventory is not verified; finding a directory does not prove that an agent loaded it.

Reviewed lifecycle actions support **Setup-owned snapshots** for:

| Agent | Setup installation | Activation and limits |
| --- | --- | --- |
| Codex | Native dedicated local marketplace on **0.167.x** | New session; exact-definition hook trust stays separate. Other release families are read-only. |
| Claude Code | Native dedicated local marketplace on **2.1.287+ in the 2.1 family**, with required JSON and data-retention flags | New session. Enabled hooks and servers can run automatically; Claude has no Codex per-hook trust gate. Existing native plugins with unverified dependency/install behavior block marketplace changes. |
| Pi | Frozen local package registered in personal `settings.json` | New session or a user-triggered reload. Setup never starts Pi or claims that a running session loaded it. Extensions can execute arbitrary code. |
| OpenCode **experimental** | Complete frozen snapshot and one native `.ts`/`.js` discovery link on managed **2.2.x** | Global-directory watchers may activate or reload the module immediately, including in running sessions. Registered does not mean verified loaded. SDK package formats, multiple entrypoints and other release families require native management. |
| Cursor, Grok Build, Muse Code, Antigravity | Detected integrations remain visible, with native-management explanations per agent | Their upstream integration can exist even when Setup lacks a verified lifecycle adapter. Use native management. |

The library shares Skills’ search, agent filters and matrix, table/cards layout, browser-saved view options, grouped phone list and rescan controls. Use **View → Show bundled and curated plugins** to hide provider defaults from the library. The choice is saved in this browser. This includes Codex’s curated marketplace packages, including separately installed packages from that marketplace; Setup-installed packages stay visible. It changes library visibility only. The source wizard offers multiple package and agent selections. One combined review covers every destination with a single code-access consent, then one install does them all, like Skills; plugin formats do not share Skills’ “Fewest copies” placement because every agent registers its own native package. Unified view groups names for browsing and asks which installation to inspect before changing settings.

A package must supply the selected agent’s own format. Codex and Claude manifests are distinct; Pi uses the `pi` resource object in `package.json`; OpenCode modules use their own TypeScript or JavaScript entrypoint. Source preview separates **integration found** from **installable with Setup**. Cursor/Antigravity manifests, Grok’s shared Claude format and OpenCode SDK package metadata are shown when found; unsupported Setup actions stay unavailable with an explanation. Experimental integrations are labelled. Setup reads all supported variants in one source snapshot. A compatible format does not guarantee that its runtime dependencies are available. Unknown execution-related manifest fields, Pi resource globs, automatic dependency installation and package scripts require native management. Codex, Claude and Pi native manifests currently need portable unscoped names; scoped OpenCode SDK package metadata is detected for native management. Project and managed scopes remain unsupported. Packages installed outside Setup are read-only.

Claude’s [native CLI contract](https://code.claude.com/docs/en/plugins/cli-reference) supplies scoped install/update/enable/disable/uninstall and JSON results; marketplace JSON results require 2.1.287. Local sources use the documented [marketplace format](https://code.claude.com/docs/en/plugins/marketplace-reference). Marketplace-add can also resolve dependencies of existing plugins, so Setup refuses that operation when it cannot verify their install behavior. This conservative preflight can require native management even for an otherwise compatible new plugin.

Pi’s [package documentation](https://pi.dev/docs/latest/packages) supports absolute local package declarations without copying or installing dependencies; [configuration](https://pi.dev/docs/latest/configuration) defines `PI_CODING_AGENT_DIR` and personal settings. Setup adds only an exact path to an immutable snapshot. Native per-resource filters are preserved by refusing to rewrite filtered declarations. OpenCode’s [plugin documentation](https://opencode.ai/docs/plugins/) and pinned [2.2.6 discovery implementation](https://raw.githubusercontent.com/anomalyco/opencode/v2.2.6/packages/core/src/plugin/source-directory.ts) explicitly load `.ts`/`.js` symlinks in the global plugin directory. Setup registers one unambiguous module through a unique owned link pointing into the complete immutable snapshot. Relative supporting-file paths stay intact. [TokenEconomizer’s upstream module](https://raw.githubusercontent.com/microsoft/TokenEconomizer/main/plugin/opencode/tokeneconomizer.ts) exports both the v1 `server` and v2 `setup` interfaces, and its [installation instructions](https://github.com/microsoft/TokenEconomizer/tree/main/plugin#opencode) recommend this symlink layout. Setup currently gates the adapter to managed 2.2.x, tested against 2.2.6. This is an experimental integration, not generic portability between OpenCode generations.

OpenCode’s native watcher may reload registration changes immediately. The library reports **Registered** or **Not registered**, based on the exact owned discovery link; project settings, policy, module compatibility and existing services can affect actual activation. Setup checks the executable version without starting a service or importing a plugin. It does not use `plugin add`, resolve npm dependencies or rewrite native JSON/JSONC settings. Configuration revisions, link ownership, resolved discovery-directory containment and source revisions are bound to each review. An externally replaced file/link or a discovery path escaping this home is refused.

The broader rollout and provider research are in [the proposal](plugins-area-proposal.md).

## Add a complete plugin

1. Choose **Install from source** and enter a public GitHub repository or an absolute folder in the container.
2. Choose the package and compatible agent targets in that source. Each target uses its own package format and installation review. Review its version, exact revision, components, automatic commands and files. Expand a file to read its text when a preview is available.
3. Confirm the installations for the selected agents. Codex and Claude use native dedicated local marketplaces; Pi uses a personal local package declaration; OpenCode uses its native discovery directory. Setup installs the frozen, reviewed files, never package-manager scripts or runtime dependencies. One combined review lists every destination with its own effects; a single consent covers all of them, and one install does them back to back.
4. Check it works. Start a new session for that agent and run the plugin’s commands — the package README lists exact names (for example, a Codex plugin may expose `$<name>:status`, a Claude plugin `/<name>:…`). OpenCode has no plugin commands in its UI: restart OpenCode if it has not reloaded the module, then check the module README for terminal commands. For Codex, use **Review hooks** to inspect and separately trust automatic commands; installation does not trust or execute those hooks. After a Codex install, the result offers **Review hooks** for the installed plugin — trusting an exact definition there is the only way its hooks run, and it never happens automatically. Claude hooks and Pi extensions can run when enabled packages load, as disclosed before installation. Service sign-in and tool permissions remain separate.

The source reader includes hidden plugin manifests and supporting files. Repository-contained Git links are materialized as ordinary files, so the installed snapshot has no link back to a mutable checkout. Escaping links, submodules, unsafe paths, oversized sources and unverified dependency/install behavior are rejected. Local folders with links are not currently supported.

Only personal installation is offered. Files and metadata survive container recreation on the home volume. Snapshots are stored below `$T3CODE_HOME/setup/plugins`; Codex and Claude keep native caches/settings in their configured homes, while Pi and OpenCode refer directly to the frozen snapshot. `CODEX_HOME`, `CLAUDE_CONFIG_DIR`, `PI_CODING_AGENT_DIR`, `OPENCODE_CONFIG_DIR` and `XDG_CONFIG_HOME` are respected. OpenCode discovery must resolve inside this container home.

## Update, disable or remove

Open a Setup-owned package to **Review update**. Setup compares the tracked repository with the installation, shows changed files and hook commands, and waits for confirmation. Disabled plugins keep their disabled setting after an update. Locally modified cache files block replacement and removal; preserve those edits first. Updates are manual. Claude updates require a changed upstream plugin version; changing bytes under the same version is rejected because its native updater may retain the old cache. Its stable marketplace and qualified native ID preserve plugin identity. Previous immutable snapshots are retained. Native provider auto-update behavior for installations outside Setup remains outside this control.

**Enable** and **Disable** change user settings for future agent sessions. Pi disables a package by removing its exact personal declaration, retaining its snapshot for re-enablement. OpenCode enables or disables its exact discovery link and reports registration, which may reload running services immediately. Other badges report user settings; project or managed policy can change what a session actually loads. Codex hook trust is unchanged; Claude, Pi and OpenCode have no equivalent per-hook trust gate.

**Remove** unregisters the selected personal installation. Codex removes its native cache. Claude uses `uninstall --keep-data`, which retains persistent data but can delete that plugin’s saved options and secrets; it does not revoke remote permissions. Pi removes only the exact owned package declaration. OpenCode removes only the owned discovery link, preserving other modules and native configuration. Source snapshots remain on disk; unrelated settings and credentials are preserved. Claude’s marketplace registration remains retained rather than using marketplace-remove, which can delete data from every plugin in that marketplace. Running sessions may retain loaded code; remote authorization is not revoked.

If a native operation fails or the server restarts partway through installation, the library reports **Needs attention**. Choose **Check installation** to reconcile Setup's tracking with the selected agent’s personal registration. Reconciliation does not execute plugin code or delete the source snapshot. For an interrupted OpenCode update, temporary tracking retains one prior record: reconciliation verifies the actual owned link and exact old/new snapshot digest, then tracks the snapshot that survived without retargeting the link. An interrupted completed removal clears tracking; an intentionally disabled installation remains owned. Temporary prior-record metadata is discarded after verification.

Plugins run with the container user's access when activated. That can include projects, home credentials and the network. This UI does not isolate plugins from one another. Use a separate restricted container/home when a package needs stronger isolation.

## Verification commands

```sh
node --test tests/plugin-inventory.test.mjs tests/plugin-providers.test.mjs tests/plugin-opencode.test.mjs tests/plugin-formats.test.mjs tests/plugins.test.mjs tests/plugins-api.test.mjs
NODE_PATH=/path/to/playwright/node_modules node scripts/plugins-ui-audit.js http://127.0.0.1:23785/__setup/
T3_PLUGIN_NATIVE_BINARY=/absolute/path/to/codex node scripts/plugins-native-smoke.mjs
T3_PLUGIN_OPENCODE_BINARY=/absolute/path/to/opencode node scripts/plugins-opencode-native-smoke.mjs
# Optional final argument: a local frozen TokenEconomizer package folder or GitHub source.
```

The browser audit uses fixture APIs, never a signed-in provider. The Codex native smoke test uses a disposable home, installs TokenEconomizer without trusting hooks, tests settings/removal, and tests an update using a controlled local package. Additional manual verification used the integrity-checked official Claude Code 2.1.321 binary in disposable homes: a dependency-free SessionStart sentinel plugin passed install, disable, enable, versioned update preserving disabled state, and removal without running its hook. TokenEconomizer’s 97-file snapshot also passed native Claude install/disable/removal and Pi declaration install/disable/removal. OpenCode 2.2.6 additionally passed the same 97-file snapshot’s registration, native activation, disable/enable, disabled update and removal, preserving relative script paths. Native activation checks used an authenticated private loopback service in a disposable home, `TE_DISABLE=1`, and no sessions, prompts, model calls or credentials. Native API state reported the plugin active after registration and absent after removal; this validation is not a claim of complete TokenEconomizer feature testing. No live sessions or production plugin settings were changed by these tests. Use the actual managed executable, not a mise shim that resolves against the disposable home.

See [cross-plugin catalog validation](plugins-validation.md) for pinned source versions, native lifecycle checks and detection limitations across eight real plugins.
